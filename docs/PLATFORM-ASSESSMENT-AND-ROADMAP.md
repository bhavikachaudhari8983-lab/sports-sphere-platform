## 1. How the existing system works

There are two separate projects.

| | Official website (`sports sphere official website`) | Registration portal (`sports sphere platform`) |
|---|---|---|
| Purpose | Public marketing site: about, sports, events calendar, sponsorship, contact | Registration, identity verification, approvals, competitions, live scoring, results |
| Tech | Static HTML/CSS/vanilla JS. Pages generated by `tools/build.py` | Next.js 15 (App Router), React 19, Prisma, NextAuth, Tailwind 4 |
| Data | `content/*.csv` or a Google Sheet, read in the browser | SQLite for development (PostgreSQL-ready); private file storage for uploads |
| Link between them | The Register buttons open `<registration_portal>/register` once that setting is filled in | — |

**Portal architecture (as built)**

```
Browser ─▶ Next.js pages (server-rendered)     ─┐
       └▶ /api/* route handlers (JSON)          ─┼─▶ src/lib/* (business rules) ─▶ Prisma ─▶ database
           every route: session + role check     │                               └▶ private uploads folder
           (src/lib/rbac.ts) + Zod validation    │
                                                  └─▶ src/services/* (external systems, behind interfaces:
                                                       ERP, DigiLocker, Aadhaar Offline e-KYC, OTP, passport,
                                                       admissions, SMS). Mocks run only in demo mode.
Every sensitive action ─▶ AuditLog
```

- **Sign-in.**
  - Staff: email and password (bcrypt), rate-limited.
  - Students: one-time code to a verified mobile or email, a PRN code, or (when configured) a university Google account.
  - Sessions are signed JWTs, re-checked against the database on every staff request.
- **Status workflow.** DRAFT → PENDING → VERIFIED (desk) → APPROVED (QR issued). Plus FLAGGED and REJECTED, each with a reason the student sees.

## 3. Known problems in the current code

| # | Problem | Effect |
|---|---|---|
| 1 | Rate limiter and DigiLocker demo state are held in memory | They only work on a single server. Use Redis when running more than one instance |
| 2 | SQLite in development | Production must use PostgreSQL (one setting change) |
| 3 | Two near-simultaneous retries of the same live-scoring tap can return an error | Rare server error at the ground |
| 4 | Result entry has no "someone else changed this" check | Two people can overwrite each other |
| 5 | Intermittent React hydration warning on the admin Competition page | Seen once in 84 tests and not reproducible. Likely cause: times formatted differently by the server and the browser |
| 6 | Official website's contact and sponsorship forms don't send anywhere | Need an endpoint or email address |
| 7 | Test note: run the browser tests with `BASE` on the same host as `NEXTAUTH_URL` | Otherwise sign-in cookies don't carry over and tests time out falsely |

**Latest test run:** 83 of 84 automated browser tests pass. The one failure is item 5.

## 4. Recommended architecture

**Keep the stack.** It already does the hardest parts (verified identity, server-side permissions, offline scoring), and a rewrite would throw that away. Add to it:

```
                     ┌──────────── Next.js app (one codebase) ────────────┐
Public & students ──▶│ public pages · registration · status               │
Staff (by role) ────▶│ admin · tournament · desk · scorer · coach · team  │
                     │                                                     │
                     │ src/lib/  business rules: registration, tournament,│
                     │           fixtures, scoring/<sport>, standings,    │
                     │           notifications, permissions               │
                     │ src/services/  ERP · DigiLocker · Offline e-KYC ·  │
                     │           email · SMS · OTP (interfaces + real)    │
                     └───────┬──────────────────────┬───────────────────────┘
                             │                      │
                     PostgreSQL (data)        Redis (rate limits, live-update fan-out)
                     private file storage     Server-Sent Events → live pages & court TVs
                     daily backups
```

1. **Tournament layer** above events. One portal runs many tournaments and keeps past seasons.
2. **Permission scopes.** A role, plus *where* it applies: platform-wide, one tournament, or one match.
3. **Scoring profiles per sport.** Each sport's rules live in their own module (event types, how the score is calculated, when a match ends). Every action is stored in an append-only log, so the score is always recalculated from that log.
4. **Notification service.** A single place sends a notice to the in-portal centre plus email, and SMS later. It's triggered by events: registration submitted, approved/rejected, fixture changed, result final.
5. **Live updates pushed with Server-Sent Events,** falling back to the current 15-second reload.
6. **Production:** PostgreSQL + Redis, private file storage (cloud storage or the university server), daily backups with a tested restore.

## 5. Database plan

**Kept as is:** StaffUser, Student, College, Document, VerificationCheck, Sport, AgeCategory, WeightCategory, Registration, DobCorrection, AgeConcern, EventChangeRequest, Measurement, WeighIn, OtpChallenge, AuditLog, DeletionRequest, Setting, Campus, School, Team, TeamMember, Placing, Certificate, Announcement.

**New and changed** (field-level detail for tournament tables is in TOURNAMENT-SYSTEM-DESIGN.md §7):

| Table | Purpose | Key relations |
|---|---|---|
| `Tournament` | Hoop It Up 2027, Summit 2027…: dates, registration open/close, status, season | has many Event |
| `Event` *(changed)* | + `tournamentId`, `registrationOpensAt/ClosesAt`, `rulesJson` (scoring settings) | belongs to Tournament, Sport |
| `RoleAssignment` | Role + scope: user X is Tournament Manager of tournament Y | StaffUser, Tournament? |
| `RegistrationField` | Extra fields an admin adds per tournament or event (e.g. "Playing position", "Jersey size", "Previous rank") with type, options, required | Tournament / Event |
| `RegistrationAnswer` | A student's answer to each extra field | Registration, RegistrationField |
| `TeamManager` / team registration | A team manager creates a squad and invites approved athletes, who accept | Team, Student/StaffUser |
| `Venue`, `Court` | Real places, used for scheduling and clash checks | Match |
| `Stage`, `Group`, `GroupEntry` | Group → knockout, Swiss, heats → final | Event → Stage → Match |
| `Match` *(changed)* | + stage, group, match number, court, statuses (postponed/cancelled/suspended/submitted/final), version, confirmed by | |
| `MatchOfficial` | Who scores and referees which match | Match, StaffUser |
| `MatchEvent` | Append-only scoring log (replaces ScoreEvent) | Match, Student? |
| `MatchCorrection` | Before/after/reason for every change to a final result | Match |
| `Protest`, `Sanction` | Disputes, withdrawals, disqualifications | Match / Event |
| `PlayerStat` | Per-player totals per match, derived from MatchEvent (points, goals, wickets…) | Match, Student |
| `Notification` | In-portal notice per user + delivery status per channel | Student / StaffUser |

Rules applied throughout:
- foreign keys everywhere
- unique indexes for one-person-one-profile and no duplicate fixtures
- a transaction for every multi-row change
- a version number on records that several people can edit
- nothing important kept only in the browser

## 6. Roles and permissions

How the requested roles map onto what already exists:

| Role | Today | Scope | Can | Can't |
|---|---|---|---|---|
| **Super Admin** | new | Platform | Everything; create admins and tournaments; system settings | (all actions audited) |
| **Sports Administrator** | = current Admin | Platform | Sports, venues, all tournaments, approvals, results, exports | Create Super Admins; see medical data |
| **Tournament Manager** | new | One tournament | Its events, fixtures, schedule, officials, results, announcements | Other tournaments; system settings |
| **Registration Manager** | new (split from Admin) | One or all tournaments | Review, flag, approve or reject registrations; confirm colleges | Fixtures, scores, settings |
| **Match Official / Referee** | = current Official (partly) | Assigned matches + desk | Desk checks, QR scan, confirm or return results | Approvals; unassigned matches |
| **Live Scorer** | new (split from Official) | **Assigned matches only** | Start and score a match, submit the result | Anything else |
| **Team Manager** | new | Own team(s) | Build the squad from approved athletes, see fixtures, lodge protests | Other teams; personal documents |
| **Coach** | ✅ exists | Own sport | View approved players, raise an age concern | Edit anything |
| **Medical** | ✅ exists | Platform | Medical declarations and certificates only | Everything else |
| **Athlete** | ✅ exists (Student) | Self | Own registration, ID, fixtures, results, certificates | Others' data |
| **Public visitor** | ✅ | — | Live scores, fixtures, standings, results; public profiles only with consent | Any personal data |

Permissions stay on the server, as today. Every page and API route checks both the role **and** the scope (for example: "is this scorer assigned to this match?").

## 7. Workflow: registration → tournament → live scoring

1. **Set-up.**
   - The Super Admin creates the tournament (dates, registration window) and assigns its managers.
   - The Tournament Manager adds events, rules, age limits, capacity, extra registration fields, venues and courts.
2. **Registration window opens.** Students register, verify their identity and choose events. A team manager builds a squad from approved athletes. Confirmation emails go out.
3. **Verification.**
   - The Registration Manager reviews flags and confirms colleges.
   - At the desk, an official measures each athlete and checks their original ID or passport → VERIFIED.
   - Approval issues the QR ID, and the athlete gets an email.
4. **Window closes.** Squads lock. Entries over capacity, or after the deadline, are refused automatically.
5. **Draw and schedule.**
   - Fixtures are generated per stage (groups → knockout).
   - The auto-scheduler places matches on courts, and the clash checker flags problems.
   - Scorers and referees are assigned, with conflict-of-interest warnings.
   - The schedule is published, and teams are notified.
6. **Match day.**
   - QR check-in.
   - The assigned scorer runs the sport's scoring screen (it works offline).
   - Spectators and court TVs update within about a second.
   - The scorer submits, then the referee confirms → FINAL.
7. **After each match.** Standings, brackets and player statistics update. Protests hold advancement until they're decided. Changes to a final result need a reason and are logged.
8. **Close.**
   - Podiums are confirmed and certificates issued.
   - Results are published (and pushed to the website's Winners board).
   - The tournament is archived into history and athlete profiles.

A full worked example (Hoop It Up, 48 teams, 94 matches, 4 courts) is in TOURNAMENT-SYSTEM-DESIGN.md §8.

## 9. Questions for the sports organisation

Already asked in the questionnaire PDF (31 questions): sports and formats, rulebooks, scorers and devices, venue internet, protests and withdrawals, spectator stats, DigiLocker, student records, SMS/email, Google sign-in, visiting universities, admins, hosting, and website content.

**New questions raised by this brief:**

1. **Teams:** who registers a team — a team manager or coach from the college, or the sports office? Can one athlete play in several teams or events?
2. **Extra fields:** which sport-specific details must the form collect (e.g. playing position, jersey number/size, previous level played)?
3. **Deadlines:** when do registrations open and close for each tournament? Are late entries ever allowed, and who can approve them?
4. **Roles:** who will hold each role (Registration Manager, Tournament Manager, Live Scorer, Team Manager)? Are scorers staff or volunteers?
5. **Email:** which official address should notifications come from, and is there an email service (Google Workspace sending, or a provider)?
6. **Public profiles:** may athlete profiles and statistics be public? Only with each athlete's consent (recommended)?
7. **History:** should past seasons' results (for example Hoop It Up 2025–26) be imported into the archive? In what format do they exist?
8. **Simultaneous tournaments:** will two tournaments ever run at the same time?
